## PHASE 1 — CRITICAL SECURITY & PRODUCTION BLOCKERS

### Objective
Eliminate immediate security vulnerabilities and production-breaking issues that expose the system to data breach, credential theft, and service compromise.

### Why This Phase Comes Here
These issues represent active vulnerabilities. If the system is deployed or accessible, attackers can exploit them right now. No other work matters until these are resolved.

### Prerequisites
None — this is the foundation.

### Affected Modules
Authentication, Configuration, File Storage, Payment Processing, SSL/TLS, Deployment

### Issues

---

#### CH-001 | P0 | Rotate APP_KEY and Delete Leaked Credentials
- **File:** `backend/.env`, `backend/.env.bak`
- **Problem:** APP_KEY is committed to git in both `.env` and `.env.bak`. Mail credentials (`MAIL_PASSWORD`) are also exposed. An attacker with the APP_KEY can decrypt all encrypted attributes (2FA secrets, recovery codes), forge sessions, and decrypt database values.
- **Required Changes:**
  1. Rotate APP_KEY immediately on production
  2. Rotate all database passwords, mail credentials, API keys
  3. Delete `backend/.env.bak`
  4. Add `.env*` and `*.bak` to `.gitignore`
  5. Check git history for leaked secrets
  6. Audit if any other keys (Stripe, WhatsApp, AWS) are exposed
- **Acceptance Criteria:**
  - `.env.bak` deleted from repo
  - `.gitignore` covers `.env*` patterns
  - APP_KEY is different from the committed value on production
  - No secrets found in git history (or are rotated)
- **Security Checks:** Full credential rotation verified
- **Tests Required:** Verify application boots with new APP_KEY; verify encrypted attributes still decrypt

#### CH-002 | P0 | Disable APP_DEBUG in Production
- **File:** `backend/.env` (line 4), `production/.env.example`
- **Problem:** `APP_DEBUG=true` exposes full stack traces, environment variables (DB credentials, API keys), and file paths to users on error pages.
- **Required Changes:**
  1. Set `APP_DEBUG=false` in all production configs
  2. Set `APP_ENV=production` in production
  3. Update `production/docker-compose.prod.yml` to enforce this
  4. Add validation in `AppServiceProvider` that prevents debug mode in production
- **Acceptance Criteria:**
  - Production environment returns generic error messages
  - Stack traces never shown to users
- **Security Checks:** Verify 500 page shows generic message

#### CH-004 | P0 | Add Rate Limiting to Auth Endpoints
- **File:** `backend/routes/api.php` (lines 148-149, 179-181)
- **Problem:** `/register`, `/login`, `/forgot-password`, `/reset-password` have NO `throttle` middleware. Unlimited brute-force attacks are possible.
- **Required Changes:**
  1. Add `throttle:5,1` to `/login`
  2. Add `throttle:3,1` to `/register`
  3. Add `throttle:3,1` to `/forgot-password`
  4. Add `throttle:3,1` to `/reset-password`
  5. Add `throttle:5,1` to `/free-trial`
  6. Add `throttle:10,1` to M-Pesa STK push endpoint
- **Acceptance Criteria:**
  - 6th login attempt within 1 minute returns 429
  - 4th password reset within 1 minute returns 429
- **Security Checks:** Rate limiting verified via curl tests

#### CH-005 | P0 | Fix 2FA Bypass — Require Code to Disable
- **File:** `backend/app/Services/TwoFactorService.php` (lines 69-91)
- **Problem:** `disable()` method accepts nullable `$code` parameter. When null/empty, 2FA code verification is skipped entirely. An attacker with only a password can disable 2FA.
- **Required Changes:**
  1. Make `$code` parameter required (non-nullable)
  2. Add validation in `DisableTwoFactorRequest` to require code
  3. Verify against TOTP or recovery codes before disabling
- **Acceptance Criteria:**
  - Disabling 2FA without a valid code returns 422
  - Both TOTP codes and recovery codes work for disabling
- **Security Checks:** Attempt disable without code — should fail

#### CH-008 | P0 | Fix M-Pesa Callback Race Condition
- **File:** `backend/app/Services/MpesaCallbackService.php` (lines 31-88)

- **Required Changes:**
  1. Add `lockForUpdate()` on the MpesaTransaction row
  2. Move the status check inside the DB transaction
  3. Use unique constraint on `checkout_request_id`
- **Acceptance Criteria:**

- **Security Checks:** Load test with concurrent callbacks

## PHASE 2 — AUTHORIZATION & ACCESS CONTROL

### Objective
Ensure every API endpoint and controller method has proper authorization checks. No user should be able to access data or perform actions beyond their role.

### Why This Phase Comes Here
Phase 1 secured the perimeter (auth, HTTPS, credentials). Phase 2 secures the interior (who can do what). Without this, any authenticated user can access any data.

### Prerequisites
Phase 1 complete

### Affected Modules
Finance, HR, LMS, Reports, Employees, Admin, Competitions

### Issues

---

#### CH-014 | P1 | Add Authorization to All Finance Controllers
- **Files:** `InvoiceController.php`, `PaymentController.php`, `ExpenseController.php`, `FeeStructureController.php`, `SubscriptionController.php`, `BudgetController.php`, `RefundController.php`
- **Problem:** None of these controllers use `$this->authorize()`, policies, or ownership checks. Any `admin|accountant` can view/edit/delete ANY invoice, reverse ANY payment, approve ANY expense.
- **Required Changes:**
  1. Create `InvoicePolicy` with owner-based rules
  2. Create `PaymentPolicy` with role-based rules
  3. Create `ExpensePolicy` with separation-of-duties rules
  4. Create `BudgetPolicy`, `FeeStructurePolicy`, `RefundPolicy`
  5. Add `$this->authorize()` calls in all controller methods
  6. Implement approval separation (submitter cannot approve)
- **Acceptance Criteria:**
  - Accountant A cannot approve Accountant A's own expense
  - Non-finance users cannot access finance endpoints
  - Admin can access all; accountant can only process, not approve own items
- **Security Checks:** Attempt cross-role access — should be denied
